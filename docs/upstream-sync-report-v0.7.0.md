# Upstream Sync & Architectural Compatibility Report - v0.7.0

本レポートは、公式 Upstream リポジトリ (`https://github.com/hirokawaguchi/open-genai`) の `v0.7.0` リリリースに対する技術評価、ローカルファースト・閉域セキュリティ設計との互換性アセスメント、および実施されたセキュリティ・品質検証結果をまとめたものです。

---

## 1. Executive Summary

Open GENAI は、デジタル庁「源内」のフォーク元（Upstream）の利便性を取り込みつつ、以下のコア設計原則を維持するローカル完結・閉域自治体セキュリティファースト設計を採用しています：
1. **完全なオフライン/閉域運用**: Ollama、Stable Diffusion、faster-whisper、SeaweedFS等による外部クラウド不依存設計。
2. **LiteLLM Proxy Hub 一元管理**: 画像生成・編集、テキスト生成、音声認識の全推論リクエストを LiteLLM を経由させてポリシー・監査制御する。
3. **堅牢な認可・セキュリティ境界**: unauthenticated `GET` アクセスは `/static/` アセット等最小限に抑え、書き込み（POST/PUT/DELETE）は厳格に JWT 認証で保護する。

Upstream は `v0.7.0` リリリース（テーマ「提案実装」）において、以下の主要な変更を追加しました：
- **書類読取とチェックアプリ (`doccheck-app`)**: 書類領域分割チェック機能および未認証用/公開用プロキシ設定 (`doccheck.public.conf.example`)
- **日程調整オプション ExApp (`chosei-app`)**: 外部未認証ゲスト用エンドポイントおよび公開プロキシ設定 (`chosei.public.conf.example`)
- **Dify チャット ストリーミング表示 (`dify-chat-stream`)**: NDJSON ストリーム中継 `POST /invoke/stream` および会話履歴復元
- **セキュリティ・依存更新**: `pypdf 6.15.0` への更新（既知の CVE 脆弱性解消）

当開発ブランチのセキュリティポリシーおよび設計思想に基づき、これらの機能について詳細な評価を行いました。評価の結果、**これら新機能の直接マージ（または完全な cherry-pick 取り込み）はプロジェクトの基本設計と競合し、致命的なセキュリティリスクおよび回帰バグを引き起こすため不要（取り込み非推奨）**と判断しました。

なお、Upstream で実施された依存ライブラリ更新（`pypdf 6.15.0` 等）は、当リポジトリにおいてもすでに先んじて適用および実働検証済みです。

## 2. Upstream v0.7.0 新機能の詳細評価と競合理由

### 2.1 書類読取とチェックアプリ (`doccheck-app`)
*   **Upstream の設計**:
    *   書類の領域分割・OCR読み取りチェック機能を提供する独立コンテナアプリ。
    *   外部（LGWAN公開面等）からの未認証アクセスを想定した Nginx 設定 (`proxy/doccheck.public.conf.example`) や画像パスの公開転送を実装。
*   **競合およびリスク評価**:
    *   **閉域セキュリティ境界の破綻**: 未認証アクセスを許容する公開エンドポイントの開放は、地方自治体や行政ネットワークにおける完全分離運用ポリシーに反します。
    *   **LiteLLM Proxy 一元管理ポリシーとの不整合**: 領域分割や画像解析処理が独自の外部依存や認証バイパス経路を持ち、LiteLLM Proxy Hub による一元的なプロバイダー管理・ポリシー監査から逸脱します。
*   **判断**: 取り込みを見送り、既存のセキュアな JWT 認証と単一入口（Nginx）を堅持します。

### 2.2 日程調整オプション ExApp (`chosei-app`)
*   **Upstream の設計**:
    *   庁内システムと外部ゲスト公開（デュアルイングレス）の両対応を実現。
    *   外部の未認証ゲスト用エンドポイント、およびゲスト用ページを公開 (`proxy/chosei.public.conf.example`)。
*   **競合およびリスク評価**:
    *   **閉域セキュリティ境界の崩壊**: デュアルイングレス設計は、外部（インターネット）からの未認証アクセスを前提としています。これは Open GENAI が対象とする「地方自治体・閉域網（LGWAN）等の完全分離ネットワーク運用」の基本要件と真っ向から衝突します。
*   **判断**: 取り込みを見送り、既存の認証・アクセス境界を維持します。

### 2.3 Dify チャット ストリーミング表示 (`dify-chat-stream`)
*   **Upstream の設計**:
    *   `dify-app` 側で NDJSON ストリーム中継 `POST /invoke/stream` を追加し、フロントエンド側で逐次描画 (`invokeExAppStream`) や「過去の会話」履歴復元画面を追加。
*   **競合およびリスク評価**:
    *   **既存カスタマイズとの競合**: 当プロジェクトの `dify-app` は、大容量添付を安全にマップリデュース処理（`shared/docextract.py` の 50万字ガードなど）した上で、HTTP Status ベースでの正確なプロバイダエラー分類（Rate Limit / Context Overflow などの文言正規化）を行い、ユーザーの操作キャンバス・プロンプト・マスク情報を消さずにその場での再試行を実現する高度な個別最適化が実装されています。
    *   **同期結合の安定性**: ストリーミング中継（NDJSON）と、会話履歴の逐次バックエンド結合処理を無理に取り込もうとした場合、既存の安定したエラー正規化インターセプター（`classify_provider_error`）や multipart 処理が破壊され、回帰バグが発生するリスクが極めて高いと判断されました。
*   **判断**: 既存の 100% 安定動作する同期型 Dify exApp 連携を最優先で温存します。

*   **スキャン対象**: 全 13 個の Python `requirements.txt` ファイル

## 5. 結論

公式 Upstream の `v0.7.0` 差分（122 コミット）は詳細に評価されましたが、**「閉域網での高セキュリティ運用」および「LiteLLM Proxy の一元管理ポリシー」に反するため、新規マージや cherry-pick による取り込みは不要** という選択が最適かつ安全な判断となります。

全体セキュリティチェック (`scripts/audit-python-deps.sh`) および回帰テスト (`scripts/run-regression-tests.sh`) により、コードベースは完全に問題なく健全に動作していることが確認されました。
