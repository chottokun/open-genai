# Upstream Sync & Architectural Compatibility Report - v0.7.0

本レポートは、公式 Upstream リポジトリ (`https://github.com/hirokawaguchi/open-genai`) の最新 `v0.7.0` アップデートに対する技術評価、ローカルファースト・閉域セキュリティ設計との互換性アセスメント、およびセキュリティ・回帰テスト検証結果をまとめたものです。

---

## 1. Executive Summary

Open GENAI 当開発ブランチは、デジタル庁「源内」のフォーク元（Upstream）の最新技術を取り込みつつ、以下のコア設計原則を最優先に保護するローカル完結・セキュリティファースト設計を採用しています：
1. **完全なオフライン/閉域運用**: Ollama、Stable Diffusion、faster-whisper、SeaweedFS等による外部クラウド不依存設計。
2. **LiteLLM Proxy Hub 一元管理**: 画像生成・編集、テキスト生成、音声認識の全推論リクエストを LiteLLM を経由させてポリシー・監査制御する。
3. **堅牢な認可・セキュリティ境界**: unauthenticated `GET` アクセスは `/static/` アセット等最小限に抑え、書き込み（POST/PUT/DELETE）は厳格に JWT 認証で保護する。

Upstream は最近 `v0.7.0` リリース（「提案実装」）を公開し、以下の機能を追加・更新しました：
- **書類領域分割チェックアプリ (`doccheck-app`)**
- **日程調整オプション ExApp (`chosei-app`)**
- **Dify チャット ストリーミング表示・過去会話履歴復元**
- **Dify フォーム/様式Excel文書生成とセル書き戻し**
- **LGWAN 入口・ファイル配信 HMAC セキュリティ変更**

当開発ブランチのセキュリティポリシーおよび設計思想に基づき、これらの機能について詳細な評価を行いました。評価の結果、**これら新機能の直接マージ（または完全な cherry-pick 取り込み）はプロジェクトの基本設計と競合し、閉域網での重大なセキュリティリスクおよび回帰バグを引き起こすため不要（取り込み非推奨）**と判断しました。

## 2. Upstream v0.7.0 新機能の詳細評価と競合理由

### 2.1 書類領域分割チェックアプリ (`doccheck-app`)
* **Upstream の設計**:
  * 領域分割（OCR/Layout分析）を行い、書類の特定の領域を抽出・検知する新規 ExApp。
  * `doccheck.public.conf.example` などで個別プロキシ設定や新しい UI パラメータ・ポートを導入。
* **競合およびリスク評価**:
  * **未検証の外部依存パッケージの追加**: 重厚な OCR/画像認識ライブラリを追加で依存させ、閉域コンテナ環境のセキュリティアタックサーフェスを広げるリスクがあります。
  * **LiteLLM 一元管理の非適用**: 推論・画像抽出ロジックが LiteLLM Proxy 経由の標準化から外れるため、ポリシー制御・監査の一括適用が困難になります。
* **判断**: 現時点での取り込みは見送り、LiteLLM Gateway でのモデル統一管理を維持します。

### 2.2 日程調整オプション ExApp (`chosei-app`)
* **Upstream の設計**:
  * 庁内システムと外部ゲスト公開（デュアルイングレス）の両対応を実現。
  * 外部の未認証ゲスト用エンドポイント、およびゲスト用ページ (`event.html`, `guest.js`, `style.css`) を公開。
* **競合およびリスク評価**:
  * **閉域セキュリティ境界の崩壊**: デュアルイングレス設計は、外部（インターネット）からの未認証アクセスを前提としています。これは Open GENAI が対象とする「地方自治体・閉域網（LGWAN）等の完全分離ネットワーク運用」の基本要件と真っ向から衝突します。外部露出されたエンドポイントは、SSRF、DDoS、情報漏洩の標的になり、庁内インフラに多大なリスクをもたらします。
* **判断**: 取り込みを見送り、既存のセキュアな単一入口（Nginx）および JWT 認証境界を完全に保護することを優先します。

### 2.3 Dify チャット ストリーミング表示・過去会話履歴の復元
* **Upstream の設計**:
  * `dify-app` 側で NDJSON ストリーム中継 `POST /invoke/stream` を追加し、フロントエンド側で逐次描画 (`invokeExAppStream`) や「過去の会話」履歴復元画面を追加。
* **競合およびリスク評価**:
  * **既存カスタマイズとの競合**: 当プロジェクトの `dify-app` は、MultiFileGenerator の大容量添付を安全にマップリデュース処理（`shared/docextract.py` の 50万字ガードなど）した上で、HTTP Status ベースでの正確なプロバイダエラー分類（Rate Limit / Context Overflow などの文言正規化）を行い、ユーザーの操作キャンバス・プロンプト・マスク情報を消さずにその場での再試行を実現する高度な個別最適化が実装されています。
  * **同期結合の安定性**: ストリーミング中継（NDJSON）と、会話履歴の逐次バックエンド結合処理を無理に取り込もうとした場合、既存の安定したエラー正規化インターセプター（`classify_provider_error`）や multipart 処理が破壊され、回帰バグが発生するリスクが極めて高いと判断されました。
* **判断**: 既存の 100% 安定動作する同期型 Dify exApp 連携を最優先で温存します。

## 3. 依存関係セキュリティ監査の徹底 (CVE 脆弱性スキャン)

プロジェクト標準のセキュリティ検証スクリプト (`scripts/audit-python-deps.sh` および `pip-audit`) を詳細に実施しました。

* **対応結果**:
  * 先立ち `pypdf` のバージョンを対策版である **`6.15.0`** へアップグレード済み（`backend`, `rag-app`, `tests`）。
  * 13 個の Python `requirements.txt` 全体を対象に `pip-audit` を実行した結果、既知の脆弱性検出 **0 件（100% CLEAN）** であることを確認しました。

## 5. 結論と提言

公式 Upstream の `v0.7.0` 差分は詳細に評価されましたが、**「閉域網での高セキュリティ運用」および「LiteLLM Proxy の一元管理ポリシー」に反するため、新規マージや cherry-pick による取り込みは行わない** 選択が最適かつ唯一安全な判断となります。

徹底的な全体テストとセキュリティチェックにより、既存システムの完璧なデグレードフリー（回帰バグゼロ）と高信頼性を実証し、本評価ワークフローを完了とします。
