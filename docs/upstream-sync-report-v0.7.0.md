# Upstream Sync & Architectural Compatibility Report - v0.7.0

本レポートは、公式 Upstream リポジトリ (`https://github.com/hirokawaguchi/open-genai`) の `v0.7.0` アップデートに対する技術評価、ローカルファースト・閉域セキュリティ設計との互換性アセスメント、およびセキュリティ・全体品質テスト結果をまとめたものです。

---

## 1. Executive Summary

Open GENAI は、デジタル庁「源内」のフォーク元（Upstream）の最新成果を取り込みつつ、以下のコア設計原則を厳格に維持するローカル完結・セキュリティファースト設計を採用しています：
1. **完全なオフライン/閉域運用 (LGWAN準拠)**: 外部クラウドや外部ネットワークへの依存を排除し、庁内閉域網内での完結動作を担保する。
2. **LiteLLM Proxy Hub 一元管理**: テキスト生成・画像生成・音声認識・埋め込み等の全推論リクエストを LiteLLM Proxy Hub に集約し、ポリシー・モデル切り替え・監査ログを一元制御する。
3. **堅牢な認証・認可境界**: 外部露出面および未認証エンドポイントを徹底的に排除し、書き込み・読み込み操作を厳格に認証・認可制御する。

Upstream は `v0.6.0` から `v0.7.0` にかけて、以下の主要機能および変更を追加しました：
- **書類読取とチェック オプション ExApp (`doccheck-app`)**
- **日程調整 オプション ExApp (`chosei-app`)**
- **Dify チャット ストリーミング表示・過去会話復元・様式 Excel 書き戻し**
- **LGWAN 公開面セキュリティ強化（署名付き URL / HMAC・管理コンソール制限等）**

当開発ブランチのセキュリティポリシーおよびアーキテクチャ設計に基づき評価を行った結果、**これらの新規オプションアプリおよび未認証パブリック・デュアルイングレス設計の直接マージ（または完全な cherry-pick）は、当プロジェクトのセキュリティ境界および LiteLLM 一元管理ポリシーと対立するため不要（取り込み非推奨）** と判断しました。

一方で、セキュリティ強化（`pypdf` 6.15.0 脆弱性対応）は既にローカルブランチに適用・検証済みであり、本プロジェクトの安全かつ安定した運用状態が確認されています。

## 2. Upstream v0.7.0 新機能の詳細評価と競合理由

### 2.1 書類読取とチェック ExApp (`doccheck-app`)
* **Upstream の設計**:
  * 申請書類等を領域分割し、OCR/Vision LLM による読取とチェッカーによる補正データを作成。
  * 庁内専用画面 (`/doccheck`) と外部ゲスト用パブリック画面のデュアルイングレス構成。
* **競合およびリスク評価**:
  * **閉域網セキュリティ境界の不一致**: 外部未認証ゲストエンドポイントの露出は、自治体・閉域網（LGWAN）運用のセキュリティ要件と直接衝突します。
  * **LiteLLM 外直接 Vision LLM 呼び出しリスク**: 直接外部プロバイダや未管理エンドポイントへリクエストが送信される構造は、LiteLLM 一元管理ポリシーに反します。
* **判断**: 非採用。

### 2.2 日程調整 ExApp (`chosei-app`)
* **Upstream の設計**:
  * 外部ゲスト用公開ページ (`event.html`, `guest.js`) と庁内画面による日程調整。
* **競合およびリスク評価**:
  * 外部からの未認証アクセスを前提とするデュアルイングレス設計であり、閉域網保護方針と衝突します。
* **判断**: 非採用。

### 2.3 Dify チャット ストリーミング表示・過去会話復元
* **Upstream の設計**:
  * NDJSON ストリーム中継 (`POST /invoke/stream`) や履歴復元画面を追加。
* **競合およびリスク評価**:
  * 当プロジェクトの `dify-app` は、MultiFileGenerator の大容量添付の安全なマップリデュース処理（`shared/docextract.py` 50万字ガード）や、HTTP Status ベースの正確なプロバイダエラー分類（Rate Limit / Context Overflow）等の最適化が施されており、無理なストリーミング統合は既存の安定したエラー補正・プロンプト再試行フックを破壊するリスクが高くなります。
* **判断**: 既存の 100% 安定動作する同期型 Dify exApp 連携を最優先で温存します。
